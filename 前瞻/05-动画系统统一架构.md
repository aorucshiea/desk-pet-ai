# 05 · 动画系统统一架构：GIF / Live2D / 3D 三后端 + 官方新主题

- **状态**：草案 v1（2026-09-30，机长已拍「先把动画系统搞好」＝**当前最高优先级**）
- **提出**：机长（2026-09-30）；**设计**：Kimi（k3）

> **机长指令原话**：先把动画系统搞好。先不删 MiniCPM 的主题，自己建一个，支持 Live2D 和 3D 以及 GIF（现在的）。我之前看到似乎有办法从 GIF 动画中提取骨架，这个提取的骨架能用吗？——问题在于即使提取骨架，模型的动作输出可能也不像人。

---

## 1. 先回答：GIF 提取的骨架能用吗

**结论：作为生产管线不成立，作为参考素材可以。** 逐层钉：

1. **GIF 是烘焙位图**。骨骼信息在逐帧渲成像素时已经不可逆丢失——「提取骨架」实际是**逐帧 2D 姿态估计**（OpenPose/MediaPipe/MMPose 系）+ 轨迹拟合。
2. **姿态估计的训练域是真人视频**。凌凌现有主题是 320px / 10fps 的像素机器猫与水滴生物——域差距下关节点输出基本是噪声，非人形角色干脆没有对应关节定义。
3. **姿态轨迹 ≠ 骨架绑定**。拿到轨迹也只有运动数据：没有部件分层、没有蒙皮权重、没有形变参数，无法驱动新角色；重定向还要再解一次体型迁移。
4. **机长的直觉命中更本质的一层**：即使轨迹干净，直接播放也是提线木偶——真实感不来自轨迹数据，来自**次级运动**（预备 anticipation、跟随 follow-through、挤压拉伸 squash&stretch、惯性、呼吸），而这些恰恰是姿态轨迹里最缺的东西。所以「不像人」不是提取质量问题，是**数据驱动播放的结构性缺失**。

**修订（2026-09-30 机长裁定，推翻初版路线）**：动画系统采用**分层混合**——基础运动（走路/跑步/加速跑/跳跃等 locomotion）走骨架驱动；复杂表现动作走视频生成 GIF（anim-engine 的 H3 管线升格为正式产能通道，不再是"降级"）。机长原案理由：**不同桌宠身体形态的表现情况差异巨大**（水滴生物与猫与人形的"呼吸/走路"在视觉上根本不是一个东西），通用物理参数覆盖不了。这正是游戏工业的成熟分层：locomotion 循环层（连续、可变速、可中断）+ full-body 表现覆盖层（离散、一次性、角色特异）。

## 2. 三后端统一架构（双平面分层，2026-09-30 机长裁定版）

```
神经系统（01 文档 L2/L1）
   organ_body / organ_embody / Laya
        │  抽象运动语义（与渲染技术无关），分两个平面：
        │
        │  【表现动作层 performance】复杂、离散、角色特异：
        │     state: working/juggling/scared/sleeping/…（一次性表演，播完回基础层）
        │  【基础运动层 locomotion】 连续、可变速、可中断：
        │     gait: idle/walk/run/fast_run/jump + speed/stride
        │  【公共参数】valence / arousal / gaze(x,y) / squash / breathing
        │
        │  02 物理世界的位移输出 (x,y,vy,grounded,tilt) 只进 locomotion 平面
─────────▼──────────────────────────────────────
AnimationBackend 接口（Electron 渲染进程内，新增模块）
  load(theme) / playPerformance(name) / setGait(gait, speed)
  setParam(k,v) / tick(dt) / dispose()
─────────┬──────────────┬──────────────┬──────
   GifBackend      Live2DBackend      ThreeDBackend
  （现有 GIF      （pixi.js +        （three.js +
   状态机收编）     pixi-live2d-display） three-vrm）
```

**两个平面在各后端的兑现**：

| 平面 | GifBackend | Live2DBackend | ThreeDBackend |
|---|---|---|---|
| **表现动作层** | **天然主场**：现有 states/reactions GIF 直接服役 | 播 motion3.json 剪辑 + 表情参数 | 播烘焙动画剪辑 + blendshape |
| **基础运动层** | 降级兑现：切步态 GIF（若主题提供；否则只平移精灵） | **参数化部件摆动**：腿摆角正弦驱动 + 身体起伏（程序写参数，天然可变速） | 程序化 walk cycle（腿骨摆动 + 骨盆起伏）或剪辑 timeScale |
| 公共参数（gaze/squash/…） | 不支持的一律忽略 | 连续参数直接映射 | 骨骼约束 / IK |

**身体形态差异的载体 = 主题自声明**（theme.json 扩展）：

- `gaitRig`：每个主题**自带**骨架定义 + 步态基元参数（猫的四肢步态、水滴的蠕动、人形的双腿，各自成文件——正是机长「不同身体有不同表现情况」的制度化）
- `performanceStates`：表现动作清单，沿用现有 `states`/`reactions` 结构的演化，视频生成管线按角色定制

兑现不了的一律**忽略不报错**——降级是设计行为，不是异常。

## 4. 动作真实感从哪来（回应「不像人」）

> **术语钉死**（2026-09-30 机长质疑后补充）：本系统所谓「物理」**不是物理仿真**（布料网格/应力求解——凌凌没有柔性身体，那条路不成立），而是**卡通物理（physicality）**——动画十二原则那套"观众以为的物理"：技术实质是把弹簧-阻尼曲线、正弦波、挤压变换作用在**变换参数**（位置/缩放/旋转/Live2D 参数值）上，不作用在网格上。全部约几十行 ODE，零碰撞体。02 文档的「刚体」同理：平台游戏规则（有地板/会掉落/会被顶起），不是 Box2D。

**程序性次级运动层**（脊髓层固有职责，不依赖任何模型）：

1. **弹簧-阻尼系统**：所有参数变化走二阶弹簧（不过冲的临界阻尼打底，情绪调制过冲量）——一个常数表就能让一切动起来"有重量"
2. **呼吸基线**：idle 状态下胸腔/身体的正弦微动 + 随机眨眼计时器（无需任何输入，永远活着）
3. **预备-跟随**：任何状态切换插 80–150ms 反向预备帧；动作结束部位依次止住（尾巴最后停）
4. **squash & stretch**：速度越大拉伸越甚，着地压缩回弹
5. **情绪调制参数形状**：valence/arousal 直接改弹簧刚度与幅度——「开心时蹦蹦跳跳」不是播不同的动画，是同一组动作在**不同物理参数**下呈现

**适用范围限定**（与机长混合裁定自洽）：程序性次级运动只作用在 **locomotion 平面与公共参数**上（走/跑/跳的姿态与物理参数形状）；**表现动作层是 GIF/剪辑的领地，不做程序化改造**——复杂表演动作的质量来自美术与视频生成，不来自参数。Live2D 的连续参数系统与 locomotion/公共参数调制是天作之合；GIF 后端在表现层继续发光，在 locomotion 层降级为步态 GIF 或纯位移。

## 5. 官方新主题（不动 MiniCPM 系，另起）

- **名称/目录**：`themes/deskpet/`（新），minicpm 残留主题不删（机长指令）
- **双平面交付清单**（一个角色的完整资产）：
  - **locomotion 层**：`gaitRig` 骨架定义 + 步态参数（走/跑/加速跑/跳）——首发 Live2D 参数化部件版；VRM 第二形态（three-vrm 程序化 walk cycle）
  - **表现动作层**：现有 states/reactions 全套 GIF 集（anim-engine H3 管线定制，角色特异的美术表现全在这层）
  - **GIF 降级包**：步态基础 GIF（无 Live2D/VRM 环境下的 fallback）
- **首发引擎：Live2D**。理由：与现有 2D 美术风格连续；参数系统天然承接 locomotion 与情绪调制；资产工作流 = 立绘拆件（可借 anim-engine 的 Qwen-Image 透明拆件管线量产草件）+ Cubism Editor 绑骨（一次性人工投入）
- 旧主题（minicpm/cybercat/zero 等）不迁移：表现动作层（GIF）继续服役，locomotion 层缺 gaitRig 时退化为现状（纯位移），行为不变
